3.1 CLAUDE.md hierarchy, scoping, modularity

What it means. Memory files load by proximity and scope: user-level ~/.claude/CLAUDE.md (that user only — not shared through version control), project-level (.claude/CLAUDE.md or root), and directory-level files for subdirectory scope.

  • Classic diagnostic: a new teammate "doesn't follow the rules" — because the rules live in someone's user-level file instead of project-level config. Location determines audience.
  • @import syntax keeps CLAUDE.md modular — import only the standards file relevant to each package.
  • .claude/rules/ directory: split a monolith into topic files (testing.md, api-conventions.md, deployment.md).
  • /memory command shows which memory files are actually loaded — the first debugging step for inconsistent behavior across sessions.
In this repo: same architecture, OpenClaw names — AGENTS.md (workspace rules), SOUL.md (persona), USER.md (single-user profile, 4,000-char budget). Files load by scope with explicit budgets, and the daily-note habit of re-reading startup files mirrors the /memory check.

3.2 Slash commands & skills

What it means. Commands and skills are packaged workflows: project-scoped in .claude/commands/ (shared via VCS) vs user-scoped in ~/.claude/commands/ (personal). Skills live in .claude/skills/ as SKILL.md with frontmatter.

  • Frontmatter options to know: context: fork (run in an isolated sub-agent so verbose or exploratory output never pollutes the main conversation), allowed-tools (restrict what the skill may touch — e.g., file-writes only), argument-hint (prompt for required parameters when invoked without args).
  • Personal variants of team skills go in ~/.claude/skills/ under different names — don't affect teammates.
  • Skills vs CLAUDE.md: skills are on-demand, task-specific workflows; CLAUDE.md is always-loaded universal standards. Choose accordingly.
In this repo: two authored skills — workshop-skills/youtube-digest-recovery/SKILL.md and memory-index-recovery/SKILL.md. Both use trigger-first descriptions ("YouTube Daily Digest automation failed — classify provider or memory-index errors…"), lean bodies, and verification criteria. One encodes allowed-tools-style restrictions in prose: "digest.py is operator-owned; never edit it."

3.3 Path-specific rules — conditional loading

What it means. Rules in .claude/rules/ can carry YAML frontmatter with paths: glob patterns; they load only when you're editing matching files — less irrelevant context, fewer tokens.

  • Glob-scoped rules beat directory-level CLAUDE.md when a convention spans directories: **/*.test.tsx catches every test file wherever it lives; terraform/**/* scopes infra rules.
  • Know when to choose path rules vs subdirectory CLAUDE.md — cross-directory conventions are the giveaway.
In this repo: the memory system uses the identical trick — repo-scoped facts carry <!-- project: path:… --> markers so project knowledge stays attached to its repo instead of leaking everywhere.

3.4 Plan mode vs direct execution

What it means. Plan mode is for exploration before commitment: large-scale changes, multiple valid approaches, architectural decisions, multi-file modifications. Direct execution is for simple, well-scoped changes.

  • Plan mode when: microservice restructuring, migrations touching 45+ files, choosing between integration approaches with different infra needs.
  • Direct when: a single-file bug fix with a clear stack trace, adding one validation conditional.
  • The Explore subagent isolates verbose discovery output and returns summaries — main context stays clean during multi-phase work.
  • Combination pattern: plan the migration, then execute the chosen plan directly.
In this repo: the study-guide build ran plan-then-execute: research and inventory first (the "explore" phase — reading exam dumps, mapping the repo), writing only after the structure was decided.

3.5 Iterative refinement techniques

What it means. How to converge on quality across turns.

  • Concrete I/O examples beat prose: when natural-language descriptions produce inconsistent results, 2–3 input/output pairs fix interpretation — the single most effective technique.
  • Test-driven iteration: write the test suite first (expected behavior, edge cases, performance), then share failures each round to guide improvement.
  • Interview pattern: have Claude ask you questions before implementing in unfamiliar domains — surfaces considerations you didn't anticipate (cache invalidation, failure modes).
  • Interacting problems → all issues in one message. Independent problems → fix sequentially.
  • Edge cases: provide specific input/expected-output pairs (e.g., null handling in migration scripts).
In this repo: the digest format rule is exactly this — "use the newest existing digest file as the format template" hands the model a concrete exemplar instead of describing the format.

3.6 Claude Code in CI/CD pipelines

What it means. Running Claude Code as an automated pipeline stage.

  • -p / --print: non-interactive mode — prevents hangs waiting for input.
  • --output-format json + --json-schema: machine-parseable structured findings, e.g., auto-posted as inline PR comments.
  • CLAUDE.md is how CI-invoked Claude gets project context: testing standards, fixture conventions, review criteria. Also feed existing tests in context so generation doesn't duplicate covered scenarios.
  • Self-review limitation: the session that generated code reviews its own changes poorly — an independent review instance (fresh context) catches more.
  • Re-run reviews with prior findings in context, instructed to report only new or still-unaddressed issues — avoids duplicate comments.
Domain takeaway: scope decides which file wins; skills package on-demand workflow with isolation options; exploration before commitment; examples and tests drive iteration; and independent reviewers beat self-review.
