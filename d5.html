5.1 Preserve critical information across long interactions

What it means. Long conversations leak facts. Three mechanisms: summarization launders specifics into vagueness; "lost in the middle" drops content buried mid-context; and tool results accumulate at full verbosity even when 5 of 40 fields matter.

  • Case-facts block: extract transactional facts (amounts, dates, order numbers, statuses) into a persistent block included in every prompt — outside the summarized history. Numbers never survive summarization reliably; keep them verbatim.
  • Lost in the middle: models use the beginning and end of long inputs reliably; mid-input findings get dropped. Mitigate: key-findings summary at the top, explicit section headers, critical items restated at the end.
  • Trim tool outputs to relevant fields before they enter context — an order lookup returning 40 fields when 5 are needed eats tokens out of proportion to value.
  • Multi-issue sessions: persist structured issue data (IDs, amounts, statuses) in a separate layer.
  • Subagents must return metadata (dates, source locations, methodology) — not bare prose — so downstream synthesis stays attributable.
  • Upstream agents with limited downstream budgets: return structured data (key facts, citations, relevance scores), not verbose reasoning chains.
In this repo: the drift incident (memory/2026-09-22.md) is the cautionary tale — a mental summary ("running all night") destroyed the timestamps and cost the agent ~12 hours of clock error. The standing fix is the case-facts pattern: trust only the timestamped envelope, and date -u before judging. Daily notes keep numbers verbatim for exactly this reason.

5.2 Escalation & ambiguity resolution

What it means. Knowing when an agent must hand off to a human — defined by triggers, not vibes.

  • Legitimate triggers: the customer explicitly asks for a human; policy is ambiguous or silent on the request (e.g., competitor price-match when policy only covers own-site); no meaningful progress is possible.
  • Illegitimate triggers: sentiment analysis and self-reported confidence scores — both unreliable proxies for actual complexity.
  • Explicit human request: escalate immediately. Don't investigate first. (Offer-to-resolve is for cases the agent can genuinely handle — and only if the customer accepts; reiterate and you escalate.)
  • Multiple customer matches: ask for additional identifiers. Never pick by heuristic — wrong-account actions are worse than one more question.
  • Encode escalation criteria in the system prompt with few-shot examples of escalate vs resolve.
In this repo: the digest-outage report rule is the same discipline: standing owner fixes (dead API keys, billing) get reported once per outage, repeated only on change — explicit triggers, no sentiment-driven spamming of the channel.

5.3 Error propagation across multi-agent systems

What it means. How failures travel from subagent to coordinator — and what the coordinator needs to recover.

  • Structured error context: failure type + what was attempted + partial results + alternatives considered. That's what enables intelligent coordinator recovery — "search unavailable" tells it nothing.
  • Access failure ≠ valid empty result (again — they really test this): timeouts need retry decisions; empty matches are successful queries. Conflating them produces phantom "no data" conclusions.
  • Both extremes are anti-patterns: silently swallowing errors (returning empty as success) and terminating the entire workflow on a single subagent failure.
  • Local first: subagents handle their own transient failures; only unresolvable errors propagate upward — with partial results and the attempt log.
  • Coverage annotations: synthesis output should mark which findings are well-supported vs which topic areas have gaps due to unavailable sources.
In this repo: the recovery skill's failure table does this end-to-end: 400 / 429 / 402 / memory-failure each carry their type, their fix path, and their owner. Partial results (the 10-video list from discovery) survive even when summarization dies — degraded delivery over all-or-nothing.

5.4 Context management in large codebase exploration

What it means. Extended exploration sessions degrade — the model starts referencing "typical patterns" instead of the specific classes it found earlier. Manage the boundary deliberately.

  • Scratchpad files persist key findings across context boundaries — the durable memory of a long exploration.
  • Subagent delegation for verbose discovery ("find all test files", "trace refund flow dependencies") — main agent keeps only high-level understanding and stays fresh.
  • Crash recovery: each agent exports state to a known location; the coordinator loads a manifest on resume — structured state persistence, not hope.
In this repo: daily notes + the digest ledger are exactly this pattern: every automation writes state (last run, sent IDs) to disk, so any future session — after any restart — resumes from facts, not memory. It's why "the digest already went out today" survives reboots.
Domain takeaway: facts live in persistent blocks and files, not summaries; escalations fire on explicit triggers; errors travel with context; and exploration writes its findings down as it goes.
