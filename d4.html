4.1 Explicit criteria to improve precision

What it means. Vague instructions produce vague precision. "Check that comments are accurate" can't be applied consistently; "flag a comment only when its claimed behavior contradicts the actual code" can — it's a categorical test, not a judgment call.

  • "Be conservative" and "only report high-confidence findings" measurably fail to improve precision — they're not criteria, they're moods.
  • Define what to report (bugs, security) and what to skip (minor style, local patterns) — category-based filtering, not confidence-based.
  • False positives aren't free: high-FP categories destroy developer trust in the accurate ones. Remediation: temporarily disable the noisy category while you fix its prompt.
  • Severity levels need concrete code examples per level, or classification drifts.
In this repo: the agent's own reply rules are categorical for exactly this reason — quiet when 23:00–08:00, when last check < 30 min ago, when nothing is new; speak when an event is < 2h away. Auditable conditions, not "be thoughtful."

4.2 Few-shot prompting

What it means. 2–4 targeted examples — the most effective technique for consistent, well-formatted output when instructions alone drift.

  • Show ambiguous cases and the reasoning for why one action beat a plausible alternative — that's how judgment generalizes to novel patterns instead of matching only pre-listed cases.
  • Demonstrate the exact output format (location, issue, severity, suggested fix) to lock consistency.
  • Include examples of acceptable patterns vs genuine issues to cut false positives without losing generalization.
  • For extraction: examples across varied document structures (inline citations vs bibliographies) reduce hallucination and empty-field problems.

4.3 Structured output via tool use & JSON schemas

What it means. The most reliable structured output isn't prompt text — it's defining an extraction tool whose input is a JSON schema, then reading the data out of the tool_use response. Syntax errors become impossible.

  • tool_choice recall: auto (model may answer in text), any (must call some tool — use when multiple schemas exist and document type is unknown), forced {"type":"tool"} (must call the named tool — use to guarantee a first extraction step).
  • Strict schemas kill syntax errors, not semantic ones: line items that don't sum to the stated total, or values in wrong fields, pass schema validation. Semantics need validation logic (→ 4.4).
  • Schema design: make fields optional/nullable when the source may not contain them — required fields invite fabrication. Add enums like "unclear" for ambiguity and "other" + a detail string for extensible categories.
  • Pair schemas with format-normalization prompt rules for messy sources.
In this repo: parallel research subagents return results through an outputSchema (JSON Schema) — merged programmatically, never parsed out of prose. The automations payloads are typed JSON for the same reason.

4.4 Validation, retry, and feedback loops

What it means. When output fails validation, retry with the error attached: original document + the failed extraction + the specific validation errors. Targeted self-correction beats blind re-asks.

  • Retries cannot create missing information. If the fact isn't in the source document (it lives in an external doc you didn't provide), no retry count will ever fix it — recognize that class early.
  • Separate semantic validation (sums wrong, field misplaced) from schema syntax errors (already eliminated by tool use).
  • Track which construct triggered each finding (detected_pattern field) — when humans dismiss findings, that field turns dismissals into a dataset for systematic false-positive analysis.
  • Self-check patterns: extract calculated_total alongside stated_total; flag mismatches; add conflict_detected booleans for inconsistent sources.

4.5 Batch processing strategies

What it means. The Message Batches API trades latency for cost — know the numbers and the constraints.

  • Numbers: 50% cost reduction; up to 24-hour processing window; no latency SLA; up to 100K requests per batch (cap may evolve — check current docs).
  • No tool use inside a batch request — you can't execute tools mid-request and feed results back. Batches are for self-contained calls.
  • Workload fit: overnight reports, weekly audits, nightly test generation — yes. Blocking pre-merge checks — no, those need synchronous.
  • Window math: e.g., submit every 4 hours to guarantee a 30-hour SLA against the 24-hour batch window.
  • custom_id correlates request/response pairs — on failure, resubmit only failed documents (chunk the ones that blew context limits).
  • Refine the prompt on a small sample first; first-pass success rate is worth more than resubmission heroics.

4.6 Multi-instance & multi-pass review

What it means. Review quality comes from independence and focus, not more thinking in the same session.

  • Self-review is structurally weak: a model that generated code carries its reasoning context — it's less likely to question its own decisions. A second, independent instance (no prior context) catches subtle issues better than self-review instructions or extended thinking.
  • Multi-pass: split large reviews into per-file local passes + cross-file integration passes (data flow, API consistency). One giant pass dilutes attention and breeds contradictory findings.
  • Verification passes: self-reported confidence per finding enables calibrated routing (high-confidence → auto-fix, low → human review).
In this repo: the guide you're reading got a second pass from a fresh session after a gateway restart killed the first — and the fresh instance immediately caught what the interrupted one couldn't verify. Independence isn't theoretical here.
Domain takeaway: criteria not moods; examples not adjectives; schemas not prose; retries only when the information exists; independence over introspection.
