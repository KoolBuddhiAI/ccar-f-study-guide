2.1 Tool interfaces: descriptions are the selection mechanism

What it means. The model picks tools by reading descriptions — nothing else. A vague description means unreliable selection; two near-identical descriptions mean misrouting.

  • Good descriptions state: purpose, input format, example queries, edge cases, and when to use this tool vs its neighbors.
  • Classic exam case: analyze_content vs analyze_document with near-identical descriptions — requests get misrouted. Fix: rename to extract_web_results with a web-specific description.
  • Fix by splitting generic tools into purpose-specific ones with defined I/O contracts: analyze_document → extract_data_points, summarize_content, verify_claim_against_source.
  • System-prompt wording interacts with selection: keyword-sensitive instructions create unintended tool associations. Review prompts for that.
In this repo: the agent's own toolset models this — every tool leads with what it's for ("Exact single-file replacements", "Fetch URL; extract readable markdown") because selection depends on it.

2.2 Structured error responses for MCP tools

What it means. When a tool fails, its job is to report the failure in a form the agent can act on. MCP signals this with the isError flag; the payload should classify the error so the model can choose recovery.

  • Error classes to memorize: transient (timeouts, unavailable), validation (bad input), business/policy ("refunds over 90 days not allowed"), permission (unauthorized).
  • Return structured metadata: errorCategory, isRetryable boolean, human-readable description. Business-rule violations get retriable: false plus a customer-friendly explanation.
  • Anti-patterns: uniform "Operation failed" responses; logging server-side and returning nothing; silent internal retries that hide the failure; raw exception text with just an isError flag.
  • Retryable vs not: returning that distinction prevents wasted retry attempts.
  • Access failure ≠ valid empty result: a timeout is a retry decision; "no matches found" is a successful query with zero rows. Conflating them corrupts downstream logic.
  • Subagents: recover transient failures locally; propagate upward only what you can't fix — with partial results and what was attempted.
In this repo: digest.py does both halves. check_quota() (l.93) returns (can_proceed, message, units_remaining) — a structured result, not a crash. The provider layer classifies: 429 → backoff + retry; 400 API_KEY_INVALID → clean abort, non-retryable. And the recovery skill's rule "never re-run the job just to test a dead key" exists precisely because retrying a non-retryable error burns quota for nothing.

2.3 Distribute tools across agents & configure tool_choice

What it means. More tools ≠ more capable. 18 tools where 4–5 would do degrades selection reliability — the decision space gets too big, and agents reach for tools outside their specialty (a synthesis agent trying web searches).

  • Scope each subagent's toolset to its role; allow limited cross-role tools for high-frequency needs (a verify_fact tool for the synthesis agent), routing complex cases through the coordinator.
  • Replace generic tools with constrained ones: fetch_url → load_document that validates document URLs.
  • tool_choice options: "auto" (model may answer in text instead), "any" (must call some tool), forced {"type":"tool","name":"..."} (must call that tool). Force a first tool (e.g., extract_metadata before enrichment), then continue in later turns.

2.4 MCP servers in Claude Code & agent workflows

What it means. MCP servers are configured per scope, discovered at connection time, and their tools are then available simultaneously.

  • Scoping: project-level .mcp.json (shared team tooling, version-controlled) vs user-level ~/.claude.json (personal/experimental).
  • Env var expansion in .mcp.json — ${GITHUB_TOKEN} — keeps credentials out of the committed file.
  • MCP resources expose content catalogs (issue summaries, doc hierarchies, DB schemas) so agents see what data exists without exploratory tool calls.
  • Prefer existing community MCP servers for standard integrations (Jira, GitHub); build custom only for team-specific workflows.
  • Enhance MCP tool descriptions so the agent prefers them over weaker built-ins when they're the better tool.

2.5 Built-in tools: Grep vs Glob vs Read/Write/Edit

What it means. Picking the right built-in is itself testable content.

  • Grep searches content (find callers of a function, locate an error string). Glob matches paths (**/*.test.tsx). Don't cross them.
  • Edit does targeted replacement on unique anchor text; when the text isn't unique, fall back to Read + Write for reliability.
  • Build understanding incrementally: Grep for entry points → Read to follow imports → trace the flow. Never read all files upfront.
In this repo: this guide was built exactly that way — grep -n 'def ' on digest.py to map functions, then reading only the quota section, instead of loading all 704 lines.
Domain takeaway: descriptions drive selection, errors are data for decisions, fewer well-scoped tools beat a big toolbox, and access failures are not empty results.
