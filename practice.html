5 Claude Code for Continuous Integration

C · Six new practice use cases

Same worlds as the exam, fresh failure modes and decision points. Tap any question to reveal the key and the reasoning.

P1 Subscription billing disputes D1 · D2 · D5

Context. Your support agent handles cancellations, failed renewals and refund requests through get_account, list_charges, issue_credit, escalate_to_human. Instrumentation shows 18% of runs end with the agent retrying issue_credit after it returned {"errorCategory":"business","isRetryable":false,"reason":"beyond 90-day window"}. Handle time triples on those cases.

Q1 · multiple choice — reveal

Most effective fix for the retry behaviour?

  1. Raise the retry limit for issue_credit so transient blips are absorbed.
  2. Instruct the agent in the system prompt to stop retrying after a failed credit.
  3. Make the business-rule error self-describing in the recovery path: keep isRetryable:false in the result, and have the agent surface the reason to the customer while offering the policy-compliant alternative.
  4. Remove issue_credit and route every refund through escalate_to_human.
Correct: C. The tool already classifies the error correctly — the failure is that nothing in the agent's recovery policy uses the classification. A non-retryable business error should end that action and become a customer-facing explanation. A and B leave the loop probabilistic; D trades away the autonomy the design depends on.
Q2 · multiple choice — reveal

"Why was I charged twice?" calls get_account, but "cancel my plan" also calls get_account when it should call list_charges. Both descriptions read "Retrieves account billing information" / "Retrieves billing records". First step?

  1. Add five few-shot examples teaching the routing.
  2. Rewrite both descriptions to state what each returns, the inputs it accepts, and when to use it instead of the other.
  3. Merge them into one billing_lookup tool.
  4. Add a keyword router that pre-selects the tool per request type.
Correct: B. Descriptions are the primary selection mechanism; B is the proportionate root-cause fix. A adds tokens without fixing ambiguity, C is a valid architecture change but far more work than a "first step", D is over-engineering that bypasses the model's language understanding.
Q3 · multiple response (select two) — reveal

One message contains three concerns: a failed charge, a wrong address on file, and a cancellation request. Which two behaviours should the agent exhibit?

  1. Decompose the request, address each concern, then synthesise one unified reply.
  2. Process concerns strictly in the order stated, escalating on the first that needs it.
  3. Persist the transactional facts (charge IDs, amounts, dates, statuses) outside summarised history.
  4. Ask the customer to resend each concern separately.
Correct: A, C. Multi-concern decomposition plus a persistent case-facts block is exactly the D1/D5 pairing. B abandons the remaining concerns; D shifts work to the customer.
Q4 · multiple choice — reveal

A goodwill credit is requested that policy doesn't cover — policy addresses only documented service outages. Correct behaviour?

  1. Escalate immediately, because policy is silent on the request.
  2. Approve it, since the customer's frustration is evident.
  3. Decline and close the conversation.
  4. Offer an unrelated discount to avoid escalation.
Correct: A. Policy gaps are an explicit escalation trigger. B and D invent policy; C is a dead end when a human could decide.
Lab P1. Four tools with differentiating descriptions, structured errors carrying errorCategory + isRetryable, a programmatic gate blocking issue_credit until get_account returns a verified ID, and a recovery policy mapping each error class to retry / explain / escalate. Done when: a non-retryable business error produces one customer-facing explanation and zero retries; multi-concern tickets get one synthesised reply.

P2 Onboarding a legacy Java monolith D3 · D5

Context. A new engineer must understand a 12-year-old monolith: mixed conventions, tests scattered beside sources. You're setting up Claude Code to help — but analysis runs flood the main session, and by the third run Claude answers about "typical service patterns" instead of this codebase's actual classes.

Q1 · multiple choice — reveal

Which change addresses the context degradation directly?

  1. Add context: fork to the analysis skill so it runs isolated and returns only its summary.
  2. Instruct the skill to summarise its output more tersely.
  3. Run /compact after each analysis.
  4. Move the skill to the personal ~/.claude/skills/ directory.
Correct: A. Isolation is the designed mechanism for keeping verbose exploration out of the main conversation. B still lands a long report; C treats symptoms after pollution; D changes scope, not isolation.
Q2 · multiple choice — reveal

Tests live beside sources throughout the tree and must follow one house style. How do you make Claude apply test conventions wherever it generates tests?

  1. Put the conventions in the root CLAUDE.md and rely on inference.
  2. Add a .claude/rules/ file with frontmatter paths: ["**/*.test.*"].
  3. Create one skill per code area containing its conventions.
  4. Add a CLAUDE.md in every subdirectory.
Correct: B. Glob-scoped rules load by path regardless of directory — the maintainable answer for cross-cutting conventions. A is unreliable inference; C needs manual invocation; D is unmaintainable across many directories.
Q3 · multiple response (select two) — reveal

One engineer wants the whole codebase read upfront; another wants incremental exploration. Which two techniques belong in the workflow?

  1. Grep for entry points and trace imports outward rather than reading everything.
  2. Keep a scratchpad file recording key findings across sessions.
  3. Cache the full source tree in the prompt for the session.
  4. Disable subagents so all context stays in one conversation.
Correct: A, B. Incremental tracing plus durable scratch notes is the D5 pattern for large codebases. C exhausts the budget and triggers lost-in-the-middle; D removes the isolation that keeps the main session clean.
Q4 · multiple choice — reveal

One module must be restructured; service boundaries are unclear and dozens of files are affected. Approach?

  1. Plan mode first: explore, map dependencies, design the boundary before editing.
  2. Direct execution, letting boundaries emerge as you edit.
  3. Direct execution with a fully pre-written per-file specification.
  4. Start direct and switch to plan mode only if problems appear.
Correct: A. Architectural, multi-file, multiple valid approaches = plan mode. B discovers dependencies too late; C presumes the answer; D ignores stated complexity.
Lab P2. Project CLAUDE.md, two rule files with glob frontmatter, one context: fork skill with allowed-tools limits, and a scratchpad convention. Done when: rules load only for matching paths, the skill's output never enters the main session, and a second session resumes from the scratchpad alone.

P3 Regulatory compliance research D1 · D2 · D5

Context. A coordinator delegates to search, document-analysis and synthesis subagents for a regulator-facing briefing. A subagent timed out; two credible sources disagree on a key figure; the synthesis must be auditable.

Q1 · multiple choice — reveal

Synthesis needs simple fact-checks (dates, names) mid-pass but round-trips through the coordinator for each — +40% latency. Best fix?

  1. Give synthesis a scoped verify_fact tool for simple lookups; complex checks still route via the coordinator.
  2. Have synthesis batch all checks to the end of the pass.
  3. Give synthesis full web-search capability.
  4. Have the search agent pre-cache speculative context around every source.
Correct: A. Least privilege for the high-frequency case, coordination preserved for the complex remainder. B creates blocking dependencies; C breaks separation of concerns; D guesses at unknown future needs.
Q2 · multiple choice — reveal

The document-analysis subagent times out. What should the coordinator receive?

  1. A generic "search unavailable" status.
  2. An empty result marked successful.
  3. Structured error context: failure type, attempted query, partial results, alternative approaches.
  4. A propagated exception that terminates the run.
Correct: C. Structured context is what enables intelligent recovery — retry differently, route around, or proceed with annotated gaps. A hides the signal, B suppresses it, D aborts work that was recoverable.
Q3 · multiple response (select two) — reveal

Two credible sources give different figures for the same statistic. The synthesis output must…

  1. Preserve both values with source attribution.
  2. Distinguish well-established findings from contested ones.
  3. Average the two values into a single number.
  4. Drop the statistic to avoid ambiguity.
Correct: A, B. Conflicting evidence is preserved and labelled, never silently resolved — the auditability requirement. C invents a number; D deletes information the reader needs.
Q4 · multiple choice — reveal

Subagents keep duplicating research. Root cause and fix?

  1. The coordinator's decomposition is too broad — narrow the subtopic partitioning per subagent.
  2. The search agent's queries are too short — lengthen them.
  3. The synthesis agent lacks deduplication instructions.
  4. The subagents share memory and overwrite each other.
Correct: A. Duplication is an assignment problem at the coordinator. B and C treat downstream symptoms; D is false — subagents don't share context.
Lab P3. Coordinator with Task in allowedTools, findings passed in-prompt, two parallel Task calls in one response, structured findings (claim, evidence, source, date), one simulated timeout, one conflicting-source case. Done when: citations survive synthesis, the timed-out section is annotated as a coverage gap, and both conflicting figures appear with attribution.

P4 Internal code-search assistant D2 · D3 · D1

Context. Engineers ask an agent to find files, trace symbols and explain modules across a monorepo. It has 19 tools, including search_code and find_files with overlapping descriptions — and a report-writing agent that keeps trying to run searches itself.

Q1 · multiple choice — reveal

Tool selection is erratic. Which change helps most?

  1. Add more tools so every phrasing has a match.
  2. Cut to the role's essential tools (~4–5) and rewrite descriptions to state inputs, outputs and boundaries.
  3. Raise the model tier.
  4. Add a keyword pre-router.
Correct: B. Selection reliability degrades with tool count; descriptions and scoping are the levers. A makes it worse; C doesn't fix ambiguity; D bypasses the model's language understanding.
Q2 · multiple choice — reveal

Which built-in tool finds all call sites of parseInvoice?

  1. Glob — it matches names across directories.
  2. Grep — content search across the tree.
  3. Read — load each candidate file.
  4. Bash ls -R.
Correct: B. Grep searches content (symbols, strings); Glob matches paths. A confuses the two; C and D don't search content.
Q3 · multiple response (select two) — reveal

Which two design moves respect the report-writing agent's role?

  1. Restrict its toolset to retrieval and formatting tools.
  2. Give it one scoped cross-role tool (verify_fact) for high-frequency needs.
  3. Grant it the full search toolset for convenience.
  4. Let it bypass the coordinator when it needs more data.
Correct: A, B. Scoped access plus one narrow, high-frequency exception. C and D destroy the specialisation that made it reliable.
Q4 · multiple choice — reveal

Exploratory questions trigger dozens of searches; the session becomes slow and vague. Best structural response?

  1. Delegate verbose exploration to subagents that return summaries.
  2. Increase the model's context window.
  3. Ask engineers to phrase questions more precisely.
  4. Disable search for complex questions.
Correct: A. Isolation keeps the main session lean and specific — the same mechanism as context: fork. B doesn't fix attention quality; C shifts burden; D removes the capability.
Lab P4. Cut 19 tools to 5 with rewritten descriptions; replace generic fetch_url with a validating load_document; add one scoped cross-role tool. Done when: ambiguous requests route correctly in a 10-case spot check, and exploration leaves the main session citing real symbol names, not generic patterns.

P5 Flaky-test triage in CI D3 · D4

Context. A CI job asks Claude to review each PR for risky changes and generate missing tests. It hangs in the pipeline, floods PRs with style nitpicks, and re-reports the same issues on every push.

Q1 · multiple choice — reveal

The job hangs waiting for input. Correct invocation?

  1. claude -p "…" — print/non-interactive mode.
  2. Export CLAUDE_HEADLESS=true.
  3. Redirect stdin from /dev/null.
  4. claude --batch "…".
Correct: A. -p is the documented non-interactive mode: process, print, exit. B and D name non-existent features; C is a Unix workaround that doesn't address the CLI contract.
Q2 · multiple choice — reveal

Findings must post as inline comments. Which combination produces machine-parseable output?

  1. --output-format json with --json-schema.
  2. A firm instruction to "reply only with JSON".
  3. Markdown tables parsed with regex.
  4. Two passes with a self-check between them.
Correct: A. Schema-enforced output is the reliable mechanism. B is probabilistic syntax; C is brittle parsing of prose; D doubles cost without guaranteeing shape.
Q3 · multiple response (select two) — reveal

Reviewers lose trust at 60% precision. Which two changes raise precision most directly?

  1. Replace "report high-confidence issues" with categorical criteria for what to report and skip.
  2. Temporarily disable the noisiest category while its prompt is reworked.
  3. Add an instruction to "be conservative".
  4. Raise the temperature.
Correct: A, B. Explicit categories, plus quarantining a noisy class while you fix it, restore trust and target the cause. C is a mood, not criteria — it measurably fails; D raises variance.
Q4 · multiple choice — reveal

A 14-file PR gets inconsistent reviews — deep on some files, contradictory across identical patterns. Restructure how?

  1. Per-file local passes plus a separate cross-file integration pass.
  2. Require engineers to split the PR.
  3. Use a larger context window on one pass.
  4. Run three passes and keep only findings that appear twice.
Correct: A. Focused passes fix attention dilution; the integration pass catches cross-file issues. B shifts burden; C confuses window size with attention quality; D suppresses real but intermittent findings.
Lab P5. CI review job with -p, --output-format json + schema for {file, line, severity, issue, suggested_fix}, categorical review criteria, and prior-findings context so re-runs report only new or unaddressed items. Done when: the job exits with no input wait, output parses without post-processing, and a second run on the same commit posts no duplicates.

P6 Insurance claim document extraction D4 · D5

Context. A pipeline processes thousands of claim documents into a downstream system. Fields are sometimes absent; a 1,200-document batch runs nightly; totals must reconcile; low-confidence extractions go to human review.

Q1 · multiple choice — reveal

Required schema fields cause the model to invent values when the document lacks the data. Best fix?

  1. Add "if unknown, leave blank" to the prompt.
  2. Mark such fields optional/nullable in the schema and permit null.
  3. Lower the temperature.
  4. Retry until the field appears.
Correct: B. Nullability in the schema is the structural fix; a prompt request fights the required-field signal. C doesn't change schema pressure; D fabricates faster.
Q2 · multiple choice — reveal

Line items must sum to the stated total. Schema validation passes but the numbers don't reconcile. Which mechanism catches this?

  1. Tighten the JSON schema further.
  2. Semantic validation: extract calculated_total alongside stated_total and flag mismatches.
  3. Add more few-shot examples.
  4. Increase max output tokens.
Correct: B. Strict schemas eliminate syntax errors, not semantic ones — reconciliation is a validation-layer job. A can't express arithmetic; C and D don't check anything.
Q3 · multiple response (select two) — reveal

Which two retry designs are sound?

  1. On validation failure, resend the document + failed extraction + the specific error.
  2. Retry when the required fact exists only in an external document not provided.
  3. Mark fields like "unclear" / "other" + detail so ambiguity is representable.
  4. Raise the batch size to absorb the failure rate.
Correct: A, C. Targeted error feedback plus representable ambiguity. B cannot succeed by construction; D multiplies cost without improving extraction.
Q4 · multiple choice — reveal

The nightly batch of 1,200 documents must finish before the morning shift; a dozen fail. Best handling?

  1. Correlate by custom_id, resubmit only the failures (chunking anything that exceeded limits).
  2. Resubmit the whole batch.
  3. Switch everything to synchronous calls.
  4. Drop the failures and reconcile later.
Correct: A. custom_id exists for exactly this; targeted resubmission preserves the 50% batch saving. B wastes the window; C abandons batch economics; D corrupts downstream totals.
Lab P6. Extraction tool with a schema (required, optional, nullable, "other"+detail, "unclear"), validation-retry with error feedback, calculated_total vs stated_total reconciliation, batch custom_id failure handling, field-level confidence routing. Done when: missing fields yield null rather than invention; a deliberate total mismatch is flagged; a failed subset is resubmitted and reconciled without reprocessing successes.

E · Readiness checklist

  • I can state the agentic loop's termination condition and name three tested anti-patterns.
  • I can explain why deterministic ordering needs programmatic gates, not prompt instructions.
  • I can describe subagent context isolation and how the coordinator must compensate.
  • I can classify a tool error as transient / validation / business / permission and say whether it's retryable.
  • I can choose between tool_choice: auto | any | forced with a reason.
  • I can place a convention correctly across CLAUDE.md levels, .claude/rules/ and skills — and say when each loads.
  • I can pick plan mode vs direct execution for a described task and justify it.
  • I can write a JSON schema with nullable and enum-"other" patterns, and say what it does not protect against.
  • I can describe when retry-with-feedback works and when it cannot.
  • I can list the Batch API's economics and its hard constraint on tool use.
  • I can name the legitimate escalation triggers — and the two unreliable proxies.
  • I can explain why an access failure isn't an empty result, and why both must be distinguishable.

Score yourself honestly; anything unticked is your next practice unit.
